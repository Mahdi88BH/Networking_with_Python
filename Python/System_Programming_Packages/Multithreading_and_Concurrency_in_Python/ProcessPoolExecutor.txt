`ProcessPoolExecutor` (part of Python’s standard `concurrent.futures` module) provides a high-level interface for 
    running asynchronous tasks across separate, independent operating system processes.

While `ThreadPoolExecutor` uses lightweight threads within a single process (which are bound to 1 CPU core by the GIL 
    for Python code), `ProcessPoolExecutor` spawns multiple Python processes, allowing your code to achieve 
    true hardware parallelism across multiple CPU cores.

---

### Core Concepts: The Pool and Worker Processes

```
                     +-----------------------------------+
                     |        ProcessPoolExecutor        |
                     |                                   |
Task Queue ------>   | [ Task 1 ] [ Task 2 ] [ Task 3 ]  |
                     |                                   |
                     |  Worker Proc 1  Worker Proc 2     |
                     +-------|--------------|------------+
                             v              v
                        CPU Core 1     CPU Core 2
                     (PID 1021 - GIL1) (PID 1022 - GIL2)

```

#### 1. Independent Python Interpreters

Unlike threads, each worker in a `ProcessPoolExecutor` is a completely standalone OS process with its own Python 
    interpreter, memory space, and Global Interpreter Lock (GIL). Because each process has its own GIL, 
    CPU-intensive Python tasks execute simultaneously on separate physical CPU cores.

#### 2. The Task Queue & IPC

When you submit a task to `ProcessPoolExecutor`:
    1. Pickling (Serialization): Python serializes (pickles) your function and its input arguments into bytes.
    2. IPC Transfer: The data is sent across process boundaries via Inter-Process Communication (IPC, like pipes/queues).
    3. Execution: An idle worker process receives the bytes, unpickles them, runs the function on a 
        dedicated CPU core, and pickles the result back to the main process.

---

### Key Functionality and Methods

- 1. Non-Blocking Task Submission (`submit`)
`executor.submit(func, *args)` hands a function to an available worker process and immediately returns a `Future` 
    object without waiting for the task to finish.

```python
future = executor.submit(heavy_calculation, data)
# ... Main process keeps executing ...
result = future.result() # Blocks until the calculation is complete
```

- 2. Parallel Mapping (`map`)
`executor.map(func, iterable)` splits a dataset across worker processes automatically, running them in parallel and 
    yielding results in the order they were submitted:

```python
results = executor.map(hash_cracker, password_list)
```

- 3. Automatic Resource Management (`with` context manager)
Using `with ProcessPoolExecutor(max_workers=4) as executor:` automatically handles process cleanup. When the `with` 
    block ends, the main script blocks until all worker processes complete their work and safely terminate.

---

### ThreadPoolExecutor vs. ProcessPoolExecutor

| Feature           | `ThreadPoolExecutor`             | `ProcessPoolExecutor`                             |
| ---               | ---                              | ---                                               |
| Execution Model   | Threads within 1 process         | Separate OS processes                             |
| GIL Bound?        | Yes (1 CPU core for Python code) | No (Bypasses GIL completely)                      |
| CPU Core Usage    | Single Core (time-sliced)        | Multiple Physical Cores                           |
| Memory Access     | Direct / Shared                  | Isolated (Requires Pickling/IPC)                  |
| Creation Overhead | Very Low (Fast)                  | High (Slower startup, higher RAM)                 |
| Best For          | Network I/O, Web Scrapers, Pings | Hash Cracking, Encryption, Math, Image Processing |

---

### Important Rules When Using `ProcessPoolExecutor`

1. Must Use `if __name__ == '__main__':` Guard:
    Because child processes re-import your main script on platforms like Windows or macOS (which use `spawn`), 
    missing this guard causes recursive process spawning loops and crashes.
2. Arguments and Functions Must Be Pickleable:
    Objects passed into `executor.submit()` or `executor.map()` (like database connections, open file handles, or complex 
    lambda functions) cannot be pickled across processes and will throw a `PicklingError`.
